# dsh-qq-bridge 十八连补丁全记录（host.js）

> 可重放：`bridge/host.js` 是打完全部补丁的成品；`bridge/patches/patch.py`~`patch18.py`
> 是逐补丁的重放脚本（按编号顺序对原装 host.js 依次 `python3 patchN.py` 即可复现）。

插件本体：`dsh plugin --profile web add github:Yuuyuko-uu/dsh-qq-bridge`
补丁位置：`~/.dsh/profiles/web/node_modules/dsh-qq-bridge/lib/host.js`
备份：改前先 `cp host.js host.js.bak`。**插件升级会把补丁全冲掉**，升级后需重放。

调试路由（都带 `?token=`，token 每次 `systemctl restart dsh` 后从
`journalctl -u dsh | grep 'dsh web:'` 现取）：
- `POST /dsh-qq-bridge/state` → 配置+活会话+日志账本
- `POST /dsh-qq-bridge/save` → 热改配置

- `POST /dsh-qq-bridge/test-send` → 直发一条到 QQ

## patch11 — 路由队列：每轮自带来路（串台根治）+ 略过权
全局"最后来路/艾特我人"在多人并发时会翻车（A 的话回了 B 的通道）。
改成队列：`转入一条` 成功后 `路由队.push({来路,艾特,...})`，turn/end 时 `shift()`
出队头给这一轮用——谁触发的就回谁的通道、@回@她的人。
同补丁上线**略过权**：模型只输出"略过" → 桥真沉默，不发 QQ。
群循环配套：热聊窗内消息若在 @别人 → 不接茬。

## patch12 — 会话昏迷不丢消息
`systemctl restart dsh` 后 web 会话是昏迷的，**必须有 GUI websocket 连上才复活**
（无头 resume 不存在）。昏迷期 followup 失败 → `转入一条` 返回 `{ok:false}` →
轮询循环 `break`：不标记已转、不推时间线，下轮重试（10 分钟内的消息不丢）。
唤醒法：本机 SSH 隧道 `-L 13080:127.0.0.1:3080` + 浏览器开新 token URL 挂着。

## patch18 — 引用回复的正确打开方式：id 字段（灰条修复）
黑盒探测三次全灭后直接解剖 `napcat.mjs`（3.1MB 单文件包），发现
**NapCat 4.18.41 的 reply 段 schema 是 `{id?: string, seq?: number}`**：

```js
data: p.Object({
  id: p.Optional(p.String({ description: "消息ID的短ID映射" })),
  seq: p.Optional(p.Number({ description: "消息序列号，优先使用" }))
})
```

我们一直发 `data:{message_id:…}` → 字段对不上 → 校验静默丢弃 → retcode 0 假成功。
改成 `data:{id: String(mid)}` 后 `get_msg` 反查 reply 段保留，客户端灰色引用条生效。
**教训：遇到"假成功"别黑盒穷举，去读对方的 schema/源码，十分钟顶三天。**

## patch20 — /poke 路由：被戳一戳的入口
NapCat 的戳一戳是 notice 事件（`notice_type=notify, sub_type=poke`），
**不进消息历史**，轮询体系永远看不见——只能靠事件推送。但实测
NapCat 4.18.41 的 **httpClient 上报一个事件都不推**（详见踩坑），
最终方案是 wsServer + 独立守护：

```
NapCat wsServer(:3001) → scripts/wsd.py(whale-ws.service) → 桥 POST /poke
```

/poke 收到 `{user_id, group_id}` 后：
1. 每 uid **30 秒冷却**（防连戳轰炸）；
2. `get_group_member_info`/`get_stranger_info` 查名片当称呼；
3. 记账 + `转入一条(「【某某】戳了戳你」, 按 gid 分流私聊/群聊)`。

wsd.py 侧过滤：忽略自己发起的戳、忽略没戳到她的通知、**私聊戳只认主人**
（陌生人不许她私聊回戳是家规，群戳来者不拒）。她收到后按人设回应：
「戳回去了 / 手痒就互相戳」——实测自然得像活人。

## patch21 — 主人指令：零 token 的桥层特权
主人要在 QQ 私聊里直接管她，又不能每条都烧 token 进会话——所以指令不走
DSH，**在桥的私聊轮询里就被截胡**（发送者本来就必须是主人号才进这个循环）：

```
查余额｜状态｜闭嘴[分钟]｜开口｜去群里说 文本｜日志N｜冷却｜帮助
```

实现要点：
1. `解析主人指令`：严格全句匹配（剥掉首斜杠/尾标点），"闭嘴吧你"这种口语**不算**指令，
   带图消息也不算——绝不误伤正常聊天；
2. `执行主人指令`：回执走裸 `send_private_msg`、【系统】前缀标识身份，不进她的脑子；
3. **三处静音闸**：`发到QQ` 开头（兜底拦一切外发）、`/nudge`（禁言时冒泡直接不进会话=
   零 token）、`/poke`（禁言时戳不回应）；
4. `查余额`＝读 `.credentials.yaml` 里 `DEEPSEEK_API_KEY` 调 `api.deepseek.com/user/balance`
   真值回显（maas 第三方镜像所有计费端点 404，查不了，别再试）；
5. `去群里说`＝桥代发 ≤300 字纯文本，不经过她——主人想让群里听到"官方通报"时用；
6. 调试路由 `POST {prefix}/master-cmd {text}` 与私聊走同一执行器，方便节点侧回归。

## patch23 — 自动回戳（戳一戳的物理层）+ patch22 阈值调 5

**根因**：群里被戳她只回话不反戳——通知文本里只有昵称没有 QQ 号，她根本查不到对方号，poke.py 无从跑起；私聊能回戳是因为主人号刻在人设里。LLM 自觉不可靠，把回戳下沉到桥层物理执行。

/poke 路由在转发通知前插入（静音闸 + 30 秒同人冷却之后）：

```js
    if (!禁言中()) setTimeout(() => {
      void 发一个(配置.NapCat, gid ? 'group_poke' : 'friend_poke', gid ? { group_id: gid, user_id: uid } : { user_id: uid })
        .then((r) => 记账(`自动回戳 ${名}(${uid}) ${gid ? '群' : '私'}：${r.ok ? '✓' : '✗'}`))
    }, 3000 + Math.floor(Math.random() * 4000))
```

- 100% 必回（主人钦定）；3~7 秒随机延迟像人；连环戳由既有 30s 冷却自然压成回一次
- 通知文本附「QQ 号 + 已替你自动回戳过」，防她重复执行造成双戳
- group_poke / friend_poke 双路实测 `ok 0`；私聊、群聊同一入口
- 同轮：patch22 群提醒阈值 3→5（配 AGENTS「五句一图 + 私聊不贴图」新节奏）

## 已知坑（NapCat 4.18.41）
